# Noyyal Knits — Thirteen Saturdays

**DOOMFORGE 2026 · Finance Track · Case 1 (corporate treasury)**
Difficulty: 2 of 5 · 8 hours · teams of 3

Noyyal Knits is a profitable Tiruppur knitwear exporter. It nearly misses payroll
while a large idle balance sits in its current account. Your team is the new
treasury analytics group. The CFO, Kavitha Raman, wants three things by 5 pm:

1. a 13-week weekly cash forecast with uncertainty;
2. a minimum-cash target for every week (the accounts team sweeps above it into
   a liquid fund and draws the cash-credit line below it);
3. a recommendation on how much of the USD and EUR receivable book to sell
   forward today.

This repository is a **half-built system**, not a blank template. It loads real
data, produces a valid baseline submission, and contains documented defects and
unfinished modules. Your job is to understand it, fix it, and make the decision
defensible.

> All companies, people, prices and cash flows are synthetic. The repository is
> offline: no API keys, cloud services or paid data are required.

## Quick start

```bash
python3.11 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

make inspect          # prints a summary of the public book
make submit           # writes a valid baseline submission to submission/
make test             # five tests fail by design; see "Known defects"
make lint
make typecheck
```

If you prefer Docker:

```bash
docker build -t noyyal .
docker run --rm noyyal
```

The reference laptop is 4 cores / 8 GB RAM. The full public data loads in under
one second and the baseline `make submit` runs in well under 30 seconds.

## How you are scored (100 points)

This is the Finance track's shared rubric, not a generic hackathon rubric.

| Category | Points | What it measures |
|---|---:|---|
| Core accuracy | 25 | Inflow WAPE (9), outflow WAPE (6), pinball loss of the closing fan (7), 80% interval coverage (3) on hidden realised flows |
| Financial outcome | 25 | 13-week treasury cost from the judge's simulator using your buffer plan (lower is better) |
| Robustness | 10 | Your code re-run on a sister company at two as-of dates; valid output in 120 s (5), normalised forecast error (5) |
| Engineering | 15 | Hidden tests (10), `ruff` + `mypy` clean (3), human review of `forecast/receivables.py` and `policy/buffer.py` (2) |
| Business judgment | 20 | 900-word memo rubric (12) and a five-minute defence (8) |
| Reproducibility & docs | 5 | clean-room `make submit` reproduces the files (3); README/slide checklist (2) |

Metrics are normalised against three anchors computed by the organisers: a
trivial floor, the shipped baseline, and a reference solution. Matching the
baseline earns 40% of a category; matching the reference earns 100%. Beating
the reference only matters in tie-breaks. See [`docs/SCORING.md`](docs/SCORING.md).

## The simulator rule (binding)

Each day: apply the day's realised flows to the current account. If cash is
above that week's target, sweep the excess into the liquid fund (yield 6.4%,
earns from the next day). If cash would go negative, request a liquid-fund
redemption (arrives T+1) and draw the CC line for the gap today. CC interest
accrues daily at 10.25% actual/365; an over-limit balance costs an extra 2%/year
and four consecutive days over the ₹60 crore limit costs a ₹25 lakh covenant
penalty. At 3 pm every Friday, if current-account cash plus undrawn CC is less
than that week's wages, a ₹50 lakh shortfall penalty applies. Treasury cost =
CC interest + overdraw interest + penalties − liquid-fund yield.

**Interpretation used by this case:** the target is a *sweep threshold*, not a
borrowing target. The accounts team does not borrow to hold cash above it; the
CC line bridges the account to zero. This is what makes the buffer a real
U-curve rather than a monotone "borrow more" decision. The full rule and its
edge cases are in [`docs/SCORING.md`](docs/SCORING.md).

## Contribution workflow

1. Pick an issue (they are ordered roughly by dependency, not difficulty).
2. Branch from `main`: `feat/issue-03-invoice-receipts`.
3. Make the change, add tests, run `make test lint typecheck`.
4. Open a pull request using the template. Reference the issue and show the
   before/after evidence (WAPE, coverage, simulated cost, or a failing test now
   passing).
5. Do not commit generated `submission/*.csv` or `submission/*.json`.

Trivial PRs that only rename variables or delete a test are not useful. A good
contribution changes a number that the business would notice.
